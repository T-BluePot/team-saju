# 팀사주 (TeamSaju)

> 팀원 생년월일시를 넣으면 개인 사주와 팀 오행 조합을 뽑아서 협업 리포트를 만들어 주는 웹

푸른핫가마(T-BluePot) 서브 프로젝트

## 뭘 만드나

팀원 생시를 넣으면 세 가지가 나온다.

1. **개인 사주 카드** 여덟 글자, 오행 분포, 협업 성향 5축
2. **팀 오행 지도** 뭐가 넘치고 뭐가 비었나
3. **팀 리포트** 우리 팀이 어떤 유형인지, 이번 주에 뭘 해볼지

밖으로 나가는 건 3번뿐이다. 개인 사주 카드와 이름은 브라우저 안에만 있고,
공유 이미지에는 팀 단위 집계만 들어간다.

## 왜 만드나

사주 앱은 죄다 1인용이고 결과가 "올해 재물운" 같은 점술로 끝난다. 팀 단위로 보는 게 없다.
MBTI 팀빌딩은 이미 질렸고, 팀 워크숍에서 아이스브레이킹 소재는 늘 모자란다.

## 핵심 설계: 계산과 해석의 분리

```
생년월일시 → [사주 엔진(코드)] → 팩트 JSON → [Claude 에이전트] → 리포트
              결정론, 테스트로 고정      간지·오행·십신    서사만 담당
```

LLM한테 "1993년 5월 3일 사주 봐줘" 하면 **간지를 지어낸다.**
그래서 여덟 글자는 절기 테이블로 코드가 확정한 뒤 AI에 넘긴다.
API 키가 없어도 룰 기반으로 리포트가 나온다.

## 팀 유형 21가지

팀 오행 분포에서 주도 오행과 결핍 오행을 뽑아 유형을 정한다.

| 주도 | 결핍 | 유형 |
|---|---|---|
| 火 | 金 | 브레이크 없는 팀. 가속만 있고 제동이 없다 |
| 木 | 金 | 끝을 못 보는 팀. 시작한 건 열 개, 끝낸 건 하나 |
| 水 | 金 | 결론이 안 나는 팀. 회의 두 시간, 정해진 건 다음 회의 날짜 |
| 土 | 火 | 체온이 낮은 팀. 다 잘 돌아가는데 아무도 안 즐겁다 |

유형마다 강점 2개, 사각지대 2개, 이번 주에 해볼 처방 2개, 그리고
"이 팀에 들어오면 좋은 사람"이 붙는다.

## 기술 스택

`barogagi-front` 컨벤션을 그대로 따른다.

| 레이어 | 선택 |
|---|---|
| 빌드 | Vite 8 |
| 프레임워크 | React 19 + TypeScript |
| 스타일 | Tailwind CSS v4 |
| 상태 | Zustand 5 |
| 애니메이션 | Framer Motion |
| 사주 계산 | lunar-typescript (절기 테이블 내장, 의존성 0) |
| 테스트 | Vitest |

## 시작하기

```bash
npm install
npm run dev      # localhost:5173
npm test         # 골든 테스트 포함
npm run build
npm run lint
```

환경변수는 `ANTHROPIC_API_KEY` 하나뿐이고 필수가 아니다. 없으면 룰 기반으로 돈다.
`VITE_` 접두사로 넣지 말 것. 클라이언트 번들에 노출된다.

## 개인정보

- v1은 **아무것도 저장하지 않는다.** localStorage도 안 쓴다. 새로고침하면 사라진다
- 생년월일은 서버로 전송하지 않는다
- 공유 이미지에는 이름도 생년월일도 들어가지 않는다
- 팀원 정보를 대신 입력할 때는 본인 동의를 받았는지 확인한다

상세는 `docs/06-privacy.md`.

## 이건 재미로 보는 콘텐츠입니다

사주는 대화를 만드는 도구다. 채용이나 평가 근거로 쓰라고 만든 게 아니다.
리포트에는 사람을 배제하는 표현이 들어가지 않고, 부정적인 지적에는 반드시
실행 가능한 제안이 함께 붙는다.

# 개발 규칙

## 브랜치

| 브랜치 | 용도 |
|---|---|
| `main` | 배포 가능한 상태. 직접 커밋 금지 |
| `develop` | 개발 통합. 기능 브랜치가 여기로 병합된다 |
| `feature/{설명}` | 새 기능 |
| `fix/{설명}` | 버그 수정 |
| `refactor/{설명}` | 동작 변경 없는 구조 개선 |
| `docs/{설명}` | 문서만 |

브랜치 이름은 영문 소문자와 하이픈을 쓴다.

```
feature/saju-engine
fix/late-zi-day-pillar
docs/privacy-spec
```

## 커밋 메시지

Conventional Commits 를 쓰되 설명은 한국어로 쓴다.

```
<타입>: <무엇을 왜 바꿨는지>
```

| 타입 | 언제 |
|---|---|
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `docs` | 문서만 |
| `style` | 포맷팅, 세미콜론 등 동작에 영향 없는 변경 |
| `refactor` | 동작 그대로 두고 구조만 |
| `test` | 테스트 추가나 수정 |
| `chore` | 빌드 설정, 의존성 |

```
feat: 야자시 처리를 sect(1)로 고정하고 골든 케이스 추가
fix: 월지 보너스가 두 번 곱해져서 土 비율이 과대평가되던 문제 수정
docs: 개인정보 처리 설계에 공유 뷰 분리 기준 추가
```

한 커밋은 한 가지만 한다. 기능과 리팩토링을 같이 넣지 않는다.

## PR

- `develop` 을 대상으로 연다. `main` 직접 PR은 릴리스할 때만
- 제목은 커밋 메시지와 같은 형식으로 쓴다
- `.github/pull_request_template.md` 를 채운다
- 리뷰어 1명 이상 승인 후 병합
- 병합은 Squash merge

## PR 전에 확인할 것

```bash
npm test         # 골든 테스트가 통과해야 한다
npm run lint
npm run build
```

계산 로직을 건드렸으면 `/verify-engine` 을 한 번 돌린다.
사용자에게 보이는 문장을 추가했으면 `/ethics-check` 를 돌린다.

## 문서가 먼저다

코드와 `docs/` 가 어긋나면 **문서를 먼저 고치고 코드를 맞춘다.**
특히 `docs/03-saju-spec.md` 는 계산 엔진의 기준 문서다.
골든 테스트의 기대값은 고치지 않는다. 테스트가 깨지면 코드가 틀린 것이다.
